# 配料表 OCR 预处理方案评估

评估日期：2026-07-23  
关联 issue：#7（map issue：#4）

## 1. 当前 pipeline 现状

- 入口：`pages/scan.py` 接收 jpg/png 上传，校验后交给 `utils/api.py`。
- 编码：`encode_image_to_base64()` 会把图片压到最长边 4000px、JPEG quality 90，再按 90→85→80→75 逐步降级，保证 base64 ≤ 2MB。
- 识别：直接调用多模态 LLM（MiMo / Agnes / Qwen-VL / GLM-4V），由模型在 system prompt 要求下同时完成「配料表区域识别 → 文字提取 → JSON 结构化」。
- 后处理：`normalize_model_output()` 与 `parse_result()` 做字段映射、清洗、本地 GB2760 评分，并用 `_tag_inferred_ingredients()` 标记模型是否自行补充了配料。

当前方案没有独立的 OCR 预处理，而是依赖 VLM 的端到端 OCR 能力。

## 2. 评估目标

1. 是否需要在送入多模态 LLM 前，先跑专用 OCR？
2. 若需要，应选 PaddleOCR / 百度 OCR / 其他？
3. 中文食品配料表常见小字、密集、反光、倾斜等场景下的准确率、部署复杂度、成本。
4. OCR 是前置提取还是仅做后校验？

## 3. 候选方案对比

| 维度 | 当前方案：纯 VLM（MiMo/Qwen/GLM-4V） | PaddleOCR 本地/自部署 | 百度 OCR 云 API |
|---|---|---|---|
| **准确率（印刷体中文小字）** | 中等；易漏字、补全、幻觉，尤其小字密集配料表 | 高；PP-OCRv5 在中文场景准确率 95%+，小字号约 82–89%（可预处理提升） | 高；官方称印刷体 98%+，高精度版约 95–99%，小字/倾斜有专项优化 |
| **准确率（手写/扭曲/反光）** | 优于传统 OCR；靠语义推理补全，但会牺牲精确性 | 低于 VLM；PP-OCRv5/PP-StructureV3 有抗干扰增强，但仍弱于大模型 | 优于传统 OCR；支持通用/高精度/手写体，复杂场景收费更高 |
| **部署复杂度** | 低；仅 HTTP API + API key | 中到高；需安装 paddlepaddle/paddleocr，管理模型文件、CUDA/CPU 版本 | 低；REST API + AK/SK，几行代码接入 |
| **运行成本** | API 按 token/次计费（已有模型费用） | 本地 GPU/CPU 一次性算力成本，推理免费 | 约 0.006–0.02 元/次，个人 500 次/月免费，企业 1000–2000 次/月 |
| **隐私/数据不出境** | 依赖第三方模型，图片上传 | 完全本地，图片不出境 | 上传百度云端 |
| **速度** | 网络延迟 + LLM 解码，通常 1–5 秒 | 本地 GPU 可做到 100–300 ms/图；CPU 较慢 | 网络延迟 + 云端处理，通常 0.5–2 秒 |
| **结构化能力** | 强；直接按 prompt 输出 JSON | 弱；仅输出文字框+文本，需额外写规则/NLP 解析配料表 | 弱；仅输出文字列表/位置，需后处理 |
| **中文/食品领域优化** | 依赖模型训练数据，无食品专项 | 中文训练充分，有版面分析、表格识别，可微调 | 中文场景覆盖广，有卡证/票据/表格专项 |
| **维护负担** | 低（模型由服务商维护） | 中（框架、模型版本、驱动依赖） | 低（百度维护） |

## 4. 详细分析

### 4.1 为什么当前纯 VLM 方案会出错

多模态 LLM 的核心目标是「理解」而非「逐字复刻」。在配料表场景中常见：

- **幻觉补全**：把模糊的「山梨糖醇」写成「山梨醇」或「山梨糖」。
- **漏字**：小字配料如「单，双甘油脂肪酸酯」漏掉「双」。
- **自由改写**：把「乙酰磺胺酸钾」写成「安赛蜜」，与原文字不符。
- **非配料混入**：把生产商地址、广告语也塞进 `ocr_text`。

这些错误对下游 GB2760 添加剂匹配和健康建议影响较大。

### 4.2 PaddleOCR

**优势**

- 开源免费，中文识别领先；PP-OCRv5 在中文印刷体场景准确率 95%+。
- 2025/2026 年新推出的 PaddleOCR-VL-1.6 在 OmniDocBench v1.6 达到 96.3%，0.9B 参数即可跑，适合本地部署。
- 支持版面分析（PP-StructureV3），可定位配料表/营养成分表区域。
- 本地部署隐私性好，离线可用。

**劣势**

- 本地部署需管理 paddlepaddle/paddleocr 环境，Windows + RTX 4090 可行，但对 Python 小白有门槛。
- 对严重反光、弯曲、手写体仍需图像预处理。
- 只能输出文字+坐标，仍需 LLM 做配料结构化。

### 4.3 百度 OCR

**优势**

- 开箱即用，HTTP API 接入简单；个人 500 次/月免费，企业认证 1000–2000 次/月。
- 中文印刷体、小字号、倾斜、反光等有长期优化，高精度版效果好。
- 无需本地维护模型和 GPU。

**劣势**

- 超出免费额度后按次计费（约 0.006–0.02 元/次）。
- 图片上传云端，对食品标签隐私敏感用户需考虑合规。
- 同样只能输出文本块，结构化仍依赖 LLM。

### 4.4 其他候选

- **EasyOCR**：安装简单，但中文准确率低于 PaddleOCR，不推荐作为主力。
- **Tesseract**：中文模型弱，需要大量预处理，不推荐。
- **腾讯云/阿里云 OCR**：能力与百度 OCR 接近，价格类似，若已在某云生态可优先考虑；否则无需额外引入。

## 5. 方案推荐

**推荐：先小范围引入百度 OCR 云 API 作为「前置 OCR 提取 + VLM 结构化」的混合方案。**

理由：

1. 部署简单，适合当前团队 Python 小白友好的要求。
2. 个人/企业免费额度足够初期验证。
3. 百度 OCR 在中文小字场景表现稳定，可显著降低 VLM 的漏字/幻觉。
4. 不替换现有 VLM，只把 OCR 结果作为补充输入，风险可控。

**更长期的本地部署路径：验证成功后，可迁移到 PaddleOCR（PP-OCRv5 或 PaddleOCR-VL）本地推理，进一步降低成本并保护隐私。**

## 6. 推荐架构

```
用户上传图片
    │
    ▼
[图像预处理]  压缩、去噪、对比度增强（复用现有 encode_image_to_base64）
    │
    ├───▶ [百度 OCR API] ──▶ 原始 ocr_text（配料表区域文字）
    │
    └───▶ [VLM / MiMo / Qwen-VL] ──▶ 结构化 JSON
                │
                └── 输入中追加 "ocr_text": "百度 OCR 识别出的原始文字"
                    并提示 LLM：优先以 ocr_text 为准，不要改写、不要补全
    │
    ▼
[本地后处理] normalize_model_output / parse_result / GB2760 评分
```

### 关键设计点

- **OCR 前置提取**：百度 OCR 先给出配料表原始文字，作为 LLM 的强约束。
- **VLM 做结构化**：仍然由 LLM 负责把配料表拆成 `ingredients`、`additives`、`nutrition_nrv` 等字段。
- **后校验机制**：若 LLM 输出的添加剂名称不在 `ocr_text` 中，标记为 `ai_inferred=true`（复用现有 `_tag_inferred_ingredients`）。
- **降级策略**：OCR 服务失败时，回退到当前纯 VLM 方案。

## 7. 原型验证计划

| 步骤 | 任务 | 产出 | 负责人/方式 |
|---|---|---|---|
| 7.1 | 在百度 AI 控制台开通「通用文字识别（高精度版）」并获取 AK/SK | 可用 API key | HITL（用户/管理员） |
| 7.2 | 采集 20–50 张真实食品配料表照片（覆盖清晰、模糊、倾斜、反光、小字） | 测试图片集 | HITL |
| 7.3 | 写一个原型脚本：百度 OCR → 输出 ocr_text；再送给当前 LLM prompt，比较与纯 VLM 的差异 | `research/ocr_prototype.py` | Agent |
| 7.4 | 评估指标：字符级准确率、添加剂召回率、AI 幻觉率、平均耗时、费用 | 评估报告 | Agent |
| 7.5 | 根据评估结果决定是否合入 `utils/api.py`，并补充 `OCR_ENABLED` 开关 | PRD / Story | Agent |

## 8. 结论

- **应增加 OCR 预处理**，但不是替代 LLM，而是作为 LLM 的输入约束和后校验依据。
- **短期首选百度 OCR 云 API**：部署简单、中文小字效果好、免费额度够用。
- **长期备选 PaddleOCR 本地部署**：降本增效、隐私可控，但部署成本更高。
- **关键改动点**：在 `pages/scan.py` 与 `utils/api.py` 之间插入可选的 OCR 提取层，并把 `ocr_text` 注入 LLM prompt。
