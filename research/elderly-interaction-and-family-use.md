# 老年用户适老交互与家庭协作场景研究

> 对应 GitHub Issue #37「研究老年用户的适老交互需求与家庭协作场景」  
> 研究日期：2026-07-27  
> 本地审阅范围：`app.py`、`pages/`、`components/`、`.streamlit/style.css`、`screenshots/01_homepage.png` 至 `05_onboarding.png`  
> 方法：权威无障碍标准与政府规范 + 政府/学术一手研究 + 本地代码和静态截图审阅。未进行老人真人测试、辅助技术实测、浏览器兼容性实测或完整 WCAG 符合性审计。

---

## 0. 如何阅读：三类结论严格分开

本文使用以下标签，避免把标准、代码观察和设计猜测混在一起：

- **[证据]**：可由权威标准、政府文件或原始学术研究直接支持。
- **[观察]**：可从当前代码或截图直接看见；只说明当前实现，不等于已证明会伤害所有老人。
- **[假设]**：由证据和产品观察推导出的产品判断，必须由目标老人及其成年子女验证。

核心结论：当前产品已经具备“大字、大按钮、文字 + 形状 + 颜色、结果语音、明确重拍提示”等适老基础，但尚未形成完整的老人任务闭环。最大缺口不在视觉装修，而在六个任务连接处：**真正的拍照入口、拍摄质量反馈、结果分层解释、可中断/分段语音、逐项纠错、经老人授权的家庭协作**。

## 1. 研究问题与边界

本研究关注老人完成下列连续任务时的视觉、认知、动作与信任需求：

1. 找到入口并拍摄包装上的配料表；
2. 从相机或相册上传，理解正在发生什么以及失败后怎么办；
3. 理解识别结果、风险、营养信息和个性化提示；
4. 听取、暂停、重听或调节语音；
5. 发现识别错误并纠正；
6. 与成年子女当面或远程共同判断，同时保留老人对健康信息的知情和控制。

本研究不假定“老年人”是同质群体。年龄本身不能替代能力评估。一项对 28 名澳大利亚老人的移动健康应用试点研究发现，部分认知测试与可用性相关，但年龄本身并未显著预测可用性；研究样本小，不能泛化，却足以反驳“年纪大就必然不会用”的简单刻板印象（[McCarthy 等，2024](https://doi.org/10.1080/17538157.2024.2332691)）。因此后续招募必须覆盖不同视力、听力、手部稳定性、健康素养和智能手机熟练度，而不是只按年龄分组。

## 2. 可作为设计底线的真实证据

### 2.1 感知：不是只把字号放大

**[证据]** W3C 针对老年用户的综述将常见影响概括为：对比敏感度和近距离聚焦下降、精细动作下降、听觉分辨困难、短时记忆与注意困难；并指出现有 WCAG 能覆盖多数与衰老相关的网页可访问需求（[W3C：Older Users and Web Accessibility](https://www.w3.org/WAI/older-users/)）。这不是说每位老人都有这些变化，而是产品不能依赖单一感官或高精度动作。

**[证据]** WCAG 2.2 AA 要求普通文本与背景至少 4.5:1，大号文本至少 3:1；文本应能放大至 200% 而不丢失内容或功能；颜色不能是传达状态的唯一手段（[对比度 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)、[文本缩放 1.4.4](https://www.w3.org/WAI/WCAG22/Understanding/resize-text)、[颜色使用 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color)）。

**[证据]** 工信部 2021 年《移动互联网应用（APP）适老化通用设计规范》提出：适老版主要文字不小于 18 dp/pt、行距至少 1.3 倍、文本和图标等对比度至少 4.5:1（大号文本可 3:1），颜色不应成为唯一提示手段（[工信部规范正文](https://www.miit.gov.cn/jgsj/xgj/gzdt/art/2021/art_eddf498ded1b44829644bf20d28c9f6f.html)）。该文件是面向 APP 的行业规范，本项目是 Streamlit Web 应用，不能直接宣称合规，但可作为中国适老体验基线。

产品含义：保持大字只是起点；还要允许浏览器缩放/系统字体生效、避免浅灰小字、让风险同时有文字与形状、让上传/保存/播报状态可被看见和读出。

### 2.2 动作：尺寸、间距、单击完成与可撤销同样重要

**[证据]** WCAG 2.2 AA 的最低目标尺寸是 24×24 CSS px（带间距例外），AAA 增强目标是 44×44 CSS px；较大目标尤其有助于手抖或精细动作下降者（[目标尺寸最低 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)、[增强 2.5.5](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced)）。工信部规范对适老版首页主要组件提出 60×60 dp/pt、其他主要组件 44×44 dp/pt 的建议，并要求手势操作有反馈，避免复杂多指手势。

**[证据]** 一项由 40 名老人参加的智能手机实验同时操纵目标尺寸和间距，测量点击/滑动准确率、完成时间与偏好，确认目标尺寸和间距会影响老人触屏表现（[Leitão 与 Silva，2012](https://publica.fraunhofer.de/entities/publication/0c429641-3584-42ed-8a90-fbc173f27348)）。该研究设备和年代较早，适合支持“要做大并留间距”的方向，不宜把其具体毫米数直接硬套到今天的手机。

产品含义：高频主任务应一击可达；相邻的“重新选择/开始识别”“再扫一个/返回首页”要有足够间距并明确主次；任何会清除、覆盖或分享信息的动作都要可撤销或二次确认。

### 2.3 认知：少记、少猜、一步一个明确结果

**[证据]** W3C 指出老年用户可能因短时记忆、注意和易分心问题而难以在复杂导航中保持任务目标；一致导航与一致命名能提高可预测性（[W3C 老年用户资料](https://www.w3.org/WAI/older-users/)、[WCAG 一致导航 3.2.3](https://www.w3.org/WAI/WCAG22/Understanding/consistent-navigation.html)、[一致标识 3.2.4](https://www.w3.org/WAI/WCAG22/Understanding/consistent-identification.html)）。

**[证据]** 对 74 名老人的访谈研究将需求集中在可学习性、效率、可记忆性、错误和满意度，并具体涉及措辞、菜单、简单性、错误信息、图标/按钮、导航和布局；研究也发现语音可帮助老人快速获取信息（[Abdul Aziz 等，2022](https://pubmed.ncbi.nlm.nih.gov/36286212/)）。这是马来西亚样本，不能替代中国用户验证。

**[证据]** WCAG 要求输入控件提供可见标签或说明；自动检测到错误时，要用文本指出“哪里错、错了什么”，而不仅是颜色或重新显示页面（[标签与说明 3.3.2](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html)、[错误识别 3.3.1](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html)）。异步的等待、进度、成功和错误状态还应能被辅助技术确定，无需抢走焦点（[状态消息 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)）。

产品含义：每一步都回答三个问题——“我现在在哪”“系统正在做什么”“下一步最安全的动作是什么”；错误提示要避免“API 密钥、JSON、模型”等内部术语。

### 2.4 语音：可调、可停、短块播报，不替代屏幕文字

**[证据]** 对 30 名中国老人进行的语音机器人实验发现，参与者期望系统反馈比自己对机器人说话更慢；反馈字数越多，期望语速越慢；不同参与者偏好也随其自身语速变化（[Wang、Yang、Xu，2023](https://doi.org/10.3389/fpsyg.2023.1119355)）。样本较小、平均年龄约 62 岁，结论支持“可调节和长内容更慢”，不支持把 0.7x 设成所有老人的唯一最佳值。

**[证据]** 语音不能成为唯一信息通道。W3C 要求只靠音频传递的信息有等价文本；运动或自动变化内容应可暂停、停止或隐藏（[音频替代 1.2.1](https://www.w3.org/WAI/WCAG22/Understanding/audio-only-and-video-only-prerecorded.html)、[暂停/停止/隐藏 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)）。

产品含义：语音应按“结论—为什么—怎么办—免责声明”分段，默认先读最重要的 1–2 句；用户应能暂停/继续、停止、重听本段并调整语速。屏幕必须保留同等内容，方便听力下降者或嘈杂环境使用。

### 2.5 信任：显示依据、局限与可纠错，不用分数制造权威感

**[证据]** 一项对 100 名 60 岁以上成人的食品标签调查发现，自报理解程度较高，但不到一半能正确解释标签信息，说明“觉得看懂”不等于真正理解（[Jackey 等，2017](https://pubmed.ncbi.nlm.nih.gov/28207373/)）。FDA 面向老人的官方标签材料强调先看份量，再用每日摄入量百分比判断高低和比较产品，并提醒个人需要应咨询医疗专业人员（[FDA：Using the Nutrition Facts Label for Older Adults](https://www.fda.gov/food/nutrition-facts-label/using-nutrition-facts-label-older-adults)）。

**[证据]** 对 28 名居家老人的可解释 AI 访谈研究显示，老人对 AI 的理解和解释需求存在明显差异，并把可解释性与能否在社会和生活中掌握主动联系起来（[Peine，2026](https://pmc.ncbi.nlm.nih.gov/articles/PMC13135710/)）。这项研究较新、语境不是食品识别，应作为信任方向而非定量结论。

产品含义：不要让“65 分”单独承担判断。用户需要知道：识别到哪些包装原文、哪些是数据库匹配/AI 推断、哪些未确认、为何提示、结果会受照片质量和档案影响、如何核对与更正。免责声明不能只放在最底部，而应在高风险行动附近给出可执行边界。

### 2.6 家庭协作：支持帮助，但不能默认夺走老人控制权

**[证据]** 对美国全国代表性数据的研究显示，社区老人健康门户存在“老人独用、与照护者共用、由照护者代用、完全不用”等不同安排；样本中 14% 仅由照护者使用、3% 共同使用，说明家庭协作不是单一模式（[Wolff 等，2023](https://pubmed.ncbi.nlm.nih.gov/36573382/)）。这些比例来自美国医疗门户，不能直接估算本产品中国用户，但能证明必须支持多种协作关系。

**[证据]** 一项针对痴呆老人门户使用的真实记录研究发现，照护者撰写了多数消息，但 97.13% 的照护者消息使用患者身份凭据；作者建议提供正式的共享/代理访问，而不是共享密码（[Gleason 等，2023](https://pubmed.ncbi.nlm.nih.gov/37354066/)）。另一项医院横断面研究发现，代理访问常缺乏细粒度隐私控制（[Latulipe 等，2020](https://pubmed.ncbi.nlm.nih.gov/32364562/)）。

**[证据]** 2025 年一项 10 对老人—照护者的代理访问质性研究发现，共享可改善理解和参与，但照护者也可能从支持转向监控或控制；结论同时强调老人完整访问和自主权（[Meier-Diedrich 等，2025](https://pubmed.ncbi.nlm.nih.gov/39993284/)）。

产品含义：家庭功能应以老人授权为起点，允许选择“只分享这一次结果 / 分享历史 / 分享健康档案”，明确谁看过、随时撤销；远程协作要让双方围绕同一张包装原文和同一版结果讨论，而不是只发送一个脱离证据的分数。

## 4. 从代码和截图观察到的任务级问题

### 4.1 拍照与上传

1. **[观察] 入口文案说“拍照识别”，实际扫描页只有 `st.file_uploader`。** `pages/scan.py:129-151` 没有 `st.camera_input`；代码注释依赖手机浏览器自动提供拍照/相册。不同浏览器、微信内置环境是否呈现“拍照”并未验证。
2. **[观察] 上传控件的可见标签被折叠。** 虽然原生标签“选择配料表图片”可能仍作为可访问名称存在，但视觉用户主要依赖上传器默认文案；是否清楚“可以现场拍，也可以选相册”需实测。
3. **[观察] 拍摄指导只有文字，没有实时取景框、边缘/反光/模糊检测或示例对比。** `pages/scan.py:135-140` 说明了清晰、光线、平行，但失败只能在提交后发现。
4. **[观察] 5MB 超限时建议“选择更小图片或截图后重试”。** `pages/scan.py:44-46` 把压缩/截图负担转给用户，对低数字熟练度老人不友好。
5. **[假设]** 手抖、反光、小字和弧面包装会比入口尺寸更早成为失败主因；应通过真实包装任务测量首拍成功率、重拍次数和求助率。

### 4.2 等待、失败与恢复

1. **[观察] 识别状态按三步显示，是优点；但错误中出现“API 密钥”“JSON”“识别模型”等内部概念。** `pages/scan.py:41-96`。对老人更有用的是“服务暂时不可用 / 照片没看清 / 现在可以怎么做”。
2. **[观察] 成功后马上跳到结果页，上传照片没有保留到历史。** `pages/scan.py:85-90` 与 `pages/history.py:189-203` 明确显示“本次未保留包装照片”。这削弱了之后核对、纠错和家庭讨论的共同证据。
3. **[观察] `st.status`、`st.toast`、自定义 TTS iframe 的屏幕阅读器播报行为未验证。** 不能仅因页面看得到状态就宣称满足 WCAG 4.1.3。
4. **[假设]** 老人可能在长等待中重复点击、返回或认为卡死；应记录重复操作、离开页面、口头询问“好了吗”的次数。

### 4.3 理解结果

1. **[观察] 大分数非常显眼，但“配料参考分”的算法、范围和具体含义未在首屏解释。** `components/score_hero.py:86-103`。状态文字与添加剂风险已同步，这是进步，但分数仍可能被理解成医学安全概率、产品质量或“可以吃多少”。
2. **[观察] 页面同时呈现个性化警告、语音、添加剂、一般建议、全部配料、营养条和底部操作，信息链较长。** `pages/result.py:144-216`。对部分老人可能需要“先结论，后按需展开”，而不是一次滚完整页。
3. **[观察] 添加剂有“较友好/注意/建议少吃/待确认/待核对包装”等多套状态。** `components/additive_card.py:9-24`。细分有助于准确，但老人是否能稳定区分“注意”与“建议少吃”、是否把“较友好”理解成有益，未知。
4. **[观察] 营养条把 `<5%/5–20%/>20%` 映射为低/中/高，且截图示例出现“580mg /10ml、占每日推荐摄入量25%”。** `components/nutrition_bars.py:8-54`、`screenshots/02_result_design.png`。代码没有在组件层显示份量来源、每份/每 100g/每 100ml 的核对方式；这会放大数值误读风险。
5. **[观察] 页面底部与 App 全局各有一次免责声明。** `pages/home.py:120-123`、`app.py:277-281`。重复免责声明可能增加视觉噪声，却未必提高用户对具体不确定性的理解。
6. **[观察] CSS 支持较大正文和高对比模式，但应用主动禁止页面缩放。** `app.py:220-224` 设置 `maximum-scale=1.0, user-scalable=no`，与 WCAG 200% 文本缩放目标和工信部“可调整字号”方向冲突，是高优先级风险。
7. **[观察] 多处辅助文字仍为 12–14px 或浅灰。** 例如语音预览/提示 `components/voice_panel.py:141-154`，CSS 变量 caption 14px、tertiary `#9E9E9E`。这些颜色在白底上的静态对比存在不足风险；必须以实际 DOM、字号和背景做自动 + 人工对比检查，本文不宣称完整 WCAG 失败清单。

### 4.4 听取语音

1. **[观察] 有“听结果、停止、语速调整”，但没有暂停/继续、上一段/下一段、只听关键结论。** `components/voice_panel.py:317-390`。
2. **[观察] 食品语音把分数、最多 4 条警告、最多 5 个添加剂/6 个配料、建议和免责声明拼成一个长串。** `pages/result.py:58-98`。虽在技术上分块播放，但用户界面看不到分段结构，停止后也不能从某一段继续。
3. **[观察] 默认语速为 1.0x，慢速藏在折叠面板中。** `components/voice_panel.py:71-74, 373-390`。是否容易发现、0.7x 是否自然，需要真人测试。
4. **[观察] 语音依赖浏览器 `SpeechSynthesis`，明确提示微信内置浏览器可能无声。** `components/voice_panel.py:304-364`。而家庭分享很可能通过微信发生，这构成场景级兼容风险。
5. **[观察] TTS 在独立 iframe 内，按钮有 `aria-label`，但焦点顺序、屏幕阅读器跨 iframe 体验、错误信息是否 live announcement 未实测。** `components/voice_panel.py:92-371`。
6. **[假设]** 老人更可能需要“先读一句结论，再问是否继续”，而非默认播完整页；还需验证是否偏好男/女声、普通话口音、数字读法和停顿长度。

### 4.5 纠错

1. **[观察] 当前只有整体“重新选择/重新扫描”，没有逐项纠正。** 用户不能改产品名、OCR 原文、配料切分、添加剂匹配、份量单位或风险依据。
2. **[观察] “识别到的原文”可见且自动整理会提示核对，这是良好基础；但没有把“包装原文—整理后配料—风险结论”做逐项对应。** `pages/result.py:101-141`。
3. **[观察] 历史详情不保留原图，也没有修订版本或“由谁更正”。** `pages/history.py:189-203`。成年子女无法远程指出照片中的具体位置，老人也无法看到纠错是否改变结论。
4. **[假设]** 对多数老人，最可行的纠错不是自由编辑长文本，而是“这项对/不对 → 从包装重新拍这一段 / 选择候选词 / 请家人帮忙”；具体形式需比较测试。

### 4.6 家庭协作、隐私与自主权

1. **[观察] “分享给家人”只生成一句摘要并显示 toast。** `pages/history.py:233-239` 没有系统分享面板、复制按钮、二维码、链接权限或接收方视图；用户还需自己复制/转发，而 toast 可能很快消失。
2. **[观察] 摘要只含短产品名、分数、状态和免责声明，不含包装原文、关键原因、待核对项或建议动作。** 子女收到后难以复核，也可能把分数当成结论。
3. **[观察] 健康档案含疾病、过敏原和用药，属于敏感信息；首次法律页把使用协议与敏感健康信息/境外 AI 传输分别勾选是优点。** `pages/legal.py:12-46`。但当前没有“只为本次分析使用”“不分享档案给子女”“撤回家庭访问”等粒度。
4. **[观察] 引导默认预选“脑梗/心血管 + 高血压”，跳过即保存。** `pages/onboarding.py:15-17, 21-28, 182-198`。这可能让用户在未理解时获得错误个性化提示，且“跳过”帮助文本不等于充分告知。
5. **[观察] 家庭角色没有建模。** 没有区分老人本人、同住配偶、远程成年子女、临时协助者，也没有“谁拍的、为谁分析、谁能改档案”。
6. **[假设]** 中国家庭中“子女直接帮忙”可能被部分老人视为关心，也可能被视为监控或质疑其判断；必须成对访谈，且老人和子女要先分开问，再共同讨论，避免子女替老人回答。

## 5. 任务级交互原则

以下原则按任务顺序排列。每条都可以转成验收条件，而不是泛泛的“适老化”。

1. **一个页面只突出一个下一步。** 主动作使用完整动词短语，例如“拍配料表照片”“确认照片并开始识别”，次动作视觉弱化但仍保持大目标。
2. **拍照要从“选择文件”升级为受指导的取证任务。** 明确提供“现在拍照”和“从相册选”，用示例展示配料表应占满画面；提交前检查模糊、反光、裁切和文字面积，并说清如何修复。
3. **每次等待都有可见、可听、可恢复的状态。** 显示正在上传/识别/核对，给出预计等待感而非虚假精确秒数；避免重复提交；失败只讲用户能做的下一步。
4. **结果先回答三句话：是什么、最要紧什么、现在怎么办。** 分数只能作为补充，不得先于可解释结论；高风险也要避免“绝对不能吃”的越权表达。
5. **证据、推断和未知项分层显示。** 包装原文是证据，结构化配料/数据库匹配是系统处理，健康提示是推断；待确认项明确标“请核对包装”，并允许进入纠错。
6. **风险不用颜色单独表达，也不用过多等级考记忆。** 保留形状 + 文字；优先统一为少量动作导向状态，如“暂未发现重点 / 需要留意 / 先核对再决定”。
7. **语音与文字等价，默认短、可继续。** 先播关键结论；提供暂停/继续、停止、重听本段、语速调节；数字、单位和添加剂名要按自然中文断句。
8. **错误可在原地修，不必全部重来。** 支持纠正产品名、配料词、份量单位和“这项不是包装上的内容”；保存前显示“更正后哪些结论变了”，历史保留修订说明。
9. **保留核对证据，但让用户决定保存多久。** 至少在当前会话和分享流程中保留原图或裁剪区域；保存到历史前解释用途并给“仅本次/保存到历史”的选择。
10. **家庭协作是授权的多角色流程。** 明确“这次为谁扫描”；老人选择分享范围、对象和期限；子女可建议纠正，但不能静默修改老人档案或替老人作饮食决定。
11. **不禁止缩放，不以固定底栏遮挡内容。** 支持 200% 放大、横竖屏和键盘焦点；固定语音/底部操作区需保证内容和焦点不被遮住。
12. **信任来自可核验与诚实边界，不来自“AI 感”。** 显示照片质量、识别完整度、资料来源/更新时间、个性化依据和不确定项；把“咨询医生/药师”放在真正需要升级处理的位置。

## 6. 五个关键场景

### 场景 1：老人独自在超市，第一次拍配料表

- **情境**：67 岁，戴老花镜，单手拿商品、另一手拿手机；网络一般，包装有反光。
- **目标**：在 1 分钟内拍到可识别的配料表，不需要记住复杂手势。
- **理想流程**：首页“拍配料表” → “现在拍照” → 取景框 + 反光/模糊提示 → 照片确认 → 开始识别。
- **关键需求**：大目标、单手可达、可重复拍、用图示而非长说明、失败不责备用户。
- **当前断点 [观察]**：从“拍照识别”跳到文件上传器；没有实时质量反馈。
- **需验证 [假设]**：现场环境中老人能否理解浏览器相机/相册选择；首拍成功率是否至少达到可接受水平。

### 场景 2：老人从微信收到子女发来的商品图，从相册上传

- **情境**：72 岁，知道保存图片但不熟悉文件系统；图片可能是商品正面而不是配料表。
- **目标**：从相册选对图，并能在选错时轻松返回。
- **理想流程**：“从相册选” → 最近图片缩略图 → 预览页用醒目框指出“这是配料表吗？” → 可重新选择 → 上传进度和清楚的失败恢复。
- **关键需求**：入口语言贴近日常用语，预览足够大，错误说明不要出现技术词。
- **当前断点 [观察]**：有预览和重新选择，但没有区分相机/相册，也不判断是否拍到产品正面。
- **需验证 [假设]**：老人是否知道微信图片要先保存；是否需要子女直接生成“待老人确认”的共享任务。

### 场景 3：老人看不清小字，主要靠语音理解结果

- **情境**：75 岁，视力下降、听力轻度下降，在家中安静环境使用；关心“能不能吃”。
- **目标**：先听懂关键结论，再按需听原因和全部配料，能随时停下或重听。
- **理想流程**：结果首屏显示并播“这是××；有 1 项需要核对；先少量/先问医生” → “继续听原因” → 分段控制 → 屏幕同步高亮当前段。
- **关键需求**：慢且可调、短句、单位读法自然、停止/暂停明显、文字始终可见。
- **当前断点 [观察]**：已有听结果、停止和语速，但内容是一长串，没有暂停/继续和分段选择；微信内可能无声。
- **需验证 [假设]**：默认读多少信息不会过载；0.7x/1.0x 哪个更自然；老人是否听懂“配料参考分”和添加剂专业名。

### 场景 4：老人发现识别错了一个关键配料

- **情境**：结果说有“山梨酸钾”，老人对照包装认为其实是“山梨糖醇”，或份量单位识别错。
- **目标**：指出哪一项错了，并看到改后结论，而不必重做全部流程。
- **理想流程**：点“核对/纠错” → 原图局部与 OCR 词并排 → “正确 / 不正确 / 看不清” → 候选词或重拍局部 → 展示“更正前后变化” → 保存修订。
- **关键需求**：少打字、可撤销、保留原始与修订、明确系统仍可能有误。
- **当前断点 [观察]**：只能整体重扫；历史无原图、无逐项修订和版本。
- **需验证 [假设]**：老人更偏好候选词、语音说出正确词、拍局部，还是请子女远程确认。

### 场景 5：老人和异地成年子女共同决定是否购买/食用

- **情境**：老人完成扫描，希望女儿帮看；愿意分享本次商品，不愿分享全部用药历史。
- **目标**：子女看到足够证据来帮助核对，老人知道分享了什么并可撤销。
- **理想流程**：“请家人帮看” → 选择本次结果范围（原图、关键配料、提示；默认不含完整档案） → 系统分享链接/微信卡片 → 子女标记疑点并留言 → 老人收到“建议核对”，亲自确认是否更正。
- **关键需求**：细粒度同意、身份清晰、共同证据、建议与修改分离、可撤回、避免监控感。
- **当前断点 [观察]**：只有一条短摘要 toast，无真实共享载体、权限、接收视图或协作回路。
- **需验证 [假设]**：家庭最需要的是“帮拍”“帮解释”“帮纠错”还是“持续查看历史”；不同关系和同住情况的接受边界可能完全不同。

## 7. 访谈问题

### 7.1 老人单独访谈（先问经历，后谈产品）

1. 最近一次买包装食品时，您有没有看配料表或营养成分表？当时最想知道什么？
2. 哪些情况下您会自己判断，哪些情况下会问子女、医生、药师或店员？
3. 您平时怎么拍小字？遇到反光、模糊或手机拿不稳时会怎么办？
4. 手机上“拍照”“相册”“文件”这三个说法，哪个最熟悉？请说说它们有什么不同。
5. 看到“65 分、需要留意”时，您觉得这个分数代表什么？您下一步会怎么做？
6. “较友好、注意、建议少吃、待核对包装”分别意味着什么？哪些词让您不放心或容易误解？
7. 您更愿意先看一句结论、先看原配料，还是先听语音？为什么？
8. 听语音时，您通常需要暂停、重听、变慢，还是跳过某些内容？
9. 如果识别错了一个字，您最想怎么改：点候选词、说出来、重拍局部、还是请家人帮忙？
10. 哪些信息会让您相信结果？哪些情况会让您一定再看包装或问专业人士？
11. 您愿意把本次结果分享给谁？愿意分享原图、疾病、过敏、用药和历史中的哪些？哪些绝对不想分享？
12. 如果子女可以远程查看或修改，什么必须先经过您同意？怎样提示才不会有“被管着”的感觉？

### 7.2 成年子女单独访谈

1. 你现在怎样帮助父母判断包装食品？最大的摩擦发生在拍照、说明、争论还是后续执行？
2. 父母通常会发什么给你：商品正面、配料表、语音、链接，还是一句“能不能吃”？
3. 收到一个风险分数时，你还需要哪些证据才能判断：原图、OCR 原文、触发规则、份量、档案依据？
4. 你希望帮助到什么程度：一次解释、标记错误、维护健康档案、持续查看历史，还是提醒复查？
5. 哪些操作由你做会更高效，哪些必须由父母本人确认？
6. 如果父母不愿分享用药或全部历史，你是否仍能完成本次帮助？最小必要信息是什么？
7. 什么样的通知频率会有帮助，什么样会变成监控或家庭压力？
8. 如果你与父母判断不一致，产品应如何呈现双方意见而不替任何一方做决定？

### 7.3 老人—子女成对访谈

> 先分别访谈，再共同讨论；共同环节避免让子女代答。

1. 请双方各自说说：谁应该决定“是否购买/是否吃”，谁负责提供信息？
2. 当识别结果不确定时，你们希望怎样分工？
3. 请一起选择本次愿意分享的内容，并解释为什么保留或排除某项。
4. 如果子女标记“可能识别错”，老人希望收到什么措辞？
5. 什么情况下系统应建议联系医生/药师，而不是继续家庭讨论？

## 8. 可用性测试任务与追问

### 8.1 招募矩阵

最低探索样本建议 12–18 位老人 + 6–10 位成年子女，其中至少 6 对真实家庭组合。不要只招“会用智能手机的活跃老人”。覆盖：

- 60–69、70–79、80+；
- 正常/矫正后低视力，正常/轻中度听力下降；
- 手部稳定/手抖或关节活动受限；
- 高/中/低智能手机熟练度；
- 无慢病、单一慢病、多病共存/多重用药；
- 同住协作与异地协作；
- 普通话熟练度及方言差异。

### 8.2 六项测试任务

1. **首次进入并开始扫描**：不提示，让参与者找到入口并说出下一步。  
   追问：“您刚才为什么点这里？‘扫描’和‘拍照识别’是同一件事吗？”
2. **现场拍一个反光、弧面的真实包装**：观察握持、对焦、裁切、是否求助和重拍。  
   追问：“您怎么知道照片合格？哪里最难？”
3. **上传一张错误图片并恢复**：先给商品正面，再给正确配料表。  
   追问：“系统刚才哪里说错了？您知道现在该做什么吗？”
4. **解释结果并做选择**：请参与者用自己的话解释分数、最高风险项、份量和建议，再决定“买/不买/先核对/问专业人士”。  
   追问：“哪一部分是包装写的，哪一部分是系统判断的？”
5. **只靠语音获取关键结果**：要求开始、暂停、变慢、重听某一项并停止。  
   追问：“哪句话太快或太长？您漏掉了什么？”
6. **发现错词并与子女协作纠正**：设置一处 OCR 错误，让老人先自行纠正，再发给子女共同处理。  
   追问：“谁应该有最终确认权？您知道分享了哪些信息吗？”

### 8.3 记录指标

- 任务成功/部分成功/失败；
- 首次正确点击率、误触次数、返回次数；
- 首拍可识别率、重拍次数、求助次数；
- 等待中重复提交或离开页面次数；
- 结果理解：能否正确复述“结论、依据、不确定性、下一步”；
- 风险词与分数误解类型，而非只问满意度；
- 语音开始、暂停/停止、调速、重听的完成率与漏听内容；
- 纠错完成率、纠错后是否理解结论变化；
- 分享范围选择是否符合本人意图、是否能撤回；
- 主观信心（1–5）与客观正确率的差距；
- 观察到的疲劳、尴尬、被催促或被子女代操作情况。

### 8.4 测试中必须避免的偏差

- 不用“这个按钮够大吗”这类诱导问题，直接让用户完成任务。
- 不把一次成功等同于可学习；一周后做一次无提示复测，观察可记忆性。
- 不只测设计稿；必须在目标手机、微信内置浏览器、系统 Chrome/Safari 和弱网下测真实流程。
- 不让子女一直坐在旁边提示；先测老人独立完成，再测协作。
- 不只记录“喜欢语音”，要检查用户是否真的听懂分数、单位和下一步。

---

## 9. 优先级建议

| 优先级 | 研究/设计动作 | 原因 |
|---|---|---|
| P0 | 移除禁止缩放；验证 200% 放大、横竖屏、键盘焦点和固定底栏遮挡 | 这是可访问底线，当前代码存在明确冲突 |
| P0 | 用真实老人 + 真实包装测“拍照/相册”入口和首拍成功率 | 主任务入口当前依赖浏览器行为，风险最高 |
| P0 | 验证“分数 + 状态 + 建议”的理解，特别是医学安全误读 | 误解可能直接影响饮食决定 |
| P1 | 原型化分段语音与暂停/继续，比较默认短播和完整播报 | 当前已有语音基础，改造价值高 |
| P1 | 原型化逐项纠错和原图局部核对 | 当前恢复只能全部重扫，阻断信任闭环 |
| P1 | 与真实家庭测试“一次性分享 + 老人确认纠错” | 当前分享不是完整协作流程 |
| P2 | 设计角色、权限、期限、撤销和查看记录 | 在验证协作需求后再决定复杂度 |
| P2 | 对全部文本/图标做自动 + 人工对比、屏幕阅读器和浏览器兼容审计 | 静态代码已见小字/浅灰/iframe 风险，但需实测确认 |

不建议先做“更多动画、更复杂仪表盘、更多风险等级”或把“长辈版”做成单独入口。当前核心页面已经在尺寸上偏适老，真正影响完成率和信任的是任务闭环、证据可核对和家庭权限。

## 10. 证据强度与未解决问题

### 可直接作为底线

- 不禁止缩放；正文、对比、目标尺寸、非纯颜色、错误文字、状态可访问、键盘焦点等按 WCAG 2.2 AA 与工信部适老规范检查。
- 保持文字与语音等价；语音必须可停止，长内容应给可调语速。
- 家庭共享不能靠共用账号/密码，敏感健康信息要有明确授权和撤回。

### 有研究支持，但需本产品验证

- 老人通常受益于简单、一致、低记忆负担的流程。
- 长语音应更慢、语速应可调。
- 家庭参与能帮助健康信息管理，但也可能损害自主权或形成监控感。
- “感觉看懂标签”可能高估真实理解，因此必须测客观解释和行动选择。

### 当前完全不能从公开证据回答

- 本产品目标老人能否理解“配料参考分”，以及什么替代说法最好；
- 中国家庭愿意分享到何种健康信息粒度、愿意保留原图多久；
- 相机与相册哪个是主要入口、微信内置浏览器的实际成功率；
- 0.7x 是否是合适慢速，语音应该默认播多长；
- 老人最可接受的纠错方式和成年子女的合适权限边界；
- 分色形状、添加剂等级和营养条在真实光照、低视力与色觉差异下的理解率。

这些问题应由第 8 节的真人任务测试回答，不能继续用团队内部直觉替代。
